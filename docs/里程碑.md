# Mini Panel 里程碑与验收标准

范围与措辞来源：能力位图的拒绝表（`internal/platform/detect.go` 与各平台实现里的
`Deny(..., "…在 Mx 交付")`）是里程碑**功能内容**的唯一依据。本文件不新增承诺：某项功能写在哪一个
里程碑，取决于它在位图里被标记成哪一句理由；要改里程碑，先改代码里的理由，再改这里。
**唯一的例外是 M5**：代码里没有任何以 "M5" 为理由的 Deny 文案（复核：
`grep -rn "M5" --include='*.go' .` 为空），M5 = "Windows 完整支持" 是项目层面的定位，
它只把已经分布在 M0/M2/M4 的 Windows 约束收敛成一个可判定的 GA 定义，不引入任何新组件。

技术决策见 `docs/技术选型与MVP规格.md`。

## M0 —— 面板自身（已完成）

交付内容：单二进制（API + 内嵌页面）、CLI 自救、引导配置、SQLite 运行态、身份与会话、
安全入口与伪装、TLS fail-closed、双提交 CSRF、登录锁定、TOTP、只追加审计、能力位图契约、
平台探测与交叉编译矩阵。

按能力位图的白名单口径（无条件白名单 `internal/platform/capabilities_test.go:179` 只含 `audit`；
`site` / `site_write` / `ssl` 从 M2 起走 `internal/platform/capabilities_test.go:217 siteWriterReady()`、`internal/platform/capabilities_test.go:231 siteTLSReady()` 的条件白名单），
M0 唯一算作"功能"的是**审计日志**；上面列的其余内容是**面板自身**的机制，不是主机管理功能。
站点、PHP、数据库、备份、防火墙写入、服务启停、终端、监控、文件权限管理在 M0 交付时的位图里全部为
`unavailable` 且带理由；从 M2 起 `php` 一项的状态改由现场探测决定（见下面的「M2 进度」），
`site` / `site_write` / `ssl` 也只在平台当场证明 nginx 可写、ACME 可用时才变为 `available`——
接口面上的站点端点也只在这些条件成立时放行，条件不成立时返回带理由的 403。

## M2 —— 站点、PHP 与站点证书

依据位图理由原文：站点创建与 Nginx 配置生成、站点写入、PHP 多版本安装、PHP 版本切换、
PHP 扩展编译安装、站点证书签发与部署（随 Nginx Provider）；Windows 侧为
"PHP 版本探测与 php-cgi 进程池管理"。

* `WebServerCtl`（`TestConfig`/`Reload`/`Restart`）与 `PHPCtl`（`Versions`/`PoolDir`/`SocketPath`）
  从声明变成实现，Linux 与 Windows 各一份，核心层仍无 `runtime.GOOS` 分支。
* 配置生成必须"先测试后生效"：`nginx -t` 之类校验不通过就不 reload，并保留可回滚的上一份配置。
* `ReloadMode` 真正参与决策：Linux `sighup`，Windows `restart_only`。
* 扩展安装按 `PHPExtInstall` 分道：Linux `package` / `source`，Windows 只允许 `prebuilt_dll`
  并校验版本 × TS/NTS × VC × 位数。
* 站点证书：手工上传、自签与 ACME HTTP-01 自动签发/续期已随第四、五片交付；
  `FeatSSL` 只在 `SiteProvider` 同时实现 `SiteACMEManager` 时置 `available`，
  只实现手工证书的构建仍保持 `degraded`。通配符只能手工上传——HTTP-01 证明不了通配符，
  DNS-01 未交付。面板自身的自签证书不算站点证书。
* 每一项写操作都要进审计（沿用 `auditWrites` 中间件），并给出快照/回滚路径。

**验收要点**：`site`、`site_write`、`php`、`php_version_switch`、`php_ext_source`、`ssl` 六个 feature
的 `available` 必须由**实际探测**得出（`Detect()` 现场验证），不许在 `newBase()` 里硬写；
`make check-honesty` 与 `make check-contract` 保持绿。

第十四片的按路径跳转表是**固定的精确路径例外表**，不是配置片段编辑器：页面只收
`path / target / code` 三个字段，每条规则由后端渲染成 `location = 路径 { return 301|302 目标$is_args$args; }`，

第十七片的两个开关回到 nginx 写入路径，因此重新套"渲染整份 vhost → `nginx -t` → 通过才 reload、

它沿用 site 能力，Provider 是否实现 `SiteBehaviorManager` 决定这两条 endpoint 是可用还是 403 capability。

第十八片的日志查看把诚实性红线放在**运行时前提**上：`nginx -t` 并不校验日志目录存在（本机

因此目录创建与属主调整（按本机 nginx.conf 的 user 指令 chown 给 worker）被放进每一次配置事务的写入前
步骤，迁移整批走一次 test-before-reload、失败全部还原；查看器对"文件尚不存在"返回 exists=false 的
真实状态，页面如实显示"尚无日志"，不假装空文件就是读成功。它不做日志切割（M6 的 cron 对象）、
不做实时 tail/WebSocket 推送、不接受调用方提交任何路径，也不动外部 vhost 的日志配置。

第十九片的自定义错误页回到"提交一张结构表、后端渲染固定指令"的写侧，诚实性红线有两条：
其一，`error_page` 只替换 **nginx 本机产生**的错误响应——反向代理站点的上游 4xx/5xx 原样透传，
面板不偷偷开启 `proxy_intercept_errors` 把上游的响应体也换掉；其二，错误页文件本身是操作者数据，
面板不代写 HTML，文件缺失时 nginx 回退内置错误页（或链到已配置的其他错误页）而不是 500——
本机 nginx 1.18 实测了静态 404、反代死上游 502、错误页文件缺失回退三种路径。这两条都写进 OpenAPI 描述与页面
对话框提示，不把"指令已写入"冒充成"访客一定能看到你的页面"。状态码闭集与路径形状校验在
normalize 与 parseMarker 两处同源执行，坏 marker 让整个文件按外部处理；空表清除始终允许。
本片不做按 location 的错误页、不做错误页文件编辑器（那是第廿二片配置文件编辑器的边界问题）、
也不做 `recursive_error_pages` 或拦截上游错误的开关。

## M3 —— 数据库

依据位图理由原文："数据库 Provider 在 M3 交付"。

* 数据库 Provider（建库、建账号、授权、改口令、备份入口）落到 `DatabaseEngines` 声明的引擎上；
  未被实现引擎不得出现在 `database_engines` 里。
* 口令只走请求体，掩码后进审计（`params_hash` 机制不变）。
* `FeatDatabase` 由探测结果决定；探测不到服务进程/socket 时报 `unavailable` 并附具体原因，
  而不是报成可用然后 500。

**验收要点**：`database` feature 打开的同时，所有数据库端点已登记规格；
删除数据库账号一类破坏性操作必须在审计里留下可辨认的 `params_hash`。

## M4 —— 主机管理：防火墙、服务、终端、监控、文件

依据位图理由原文：防火墙规则写入、服务启停、Web 终端与录像审计、监控采集与图表、
文件权限（属主/模式）管理随文件管理器、SSH/RDP 访问管理页；Windows 防火墙 Provider。

* `FirewallCtl` 的 `Snapshot()` / `Restore()` 是**强制**要求（见 `internal/platform/paths.go`
  接口注释）：改规则前必须能拿到可还原的快照，先装"把自己锁在门外"的保险。
  默认不得关闭面板所在端口。
* `service_write` 与 `firewall_write` 这类"能不能改"的子 feature 与只读态分开灰度。
* Web 终端走那一条预留的 WebSocket 通道；因此**不得**给 HTTP Server 加全局 `WriteTimeout`
  （`cmd/minipanel/main.go` 的注释已钉住这一点）。
* 终端必须录像并进审计；监控采集只读，不进 `auditWrites` 的写记录。
* 文件权限管理在 POSIX 上暴露属主/模式，在 Windows 上不得出现 chmod 类控件
  （`Permissions=acl`，`FeatFilePerms` 保持拒绝）。

**验收要点**：`firewall`、`firewall_write`、`service_write`、`terminal`、`monitor`、
`file_posix_perms`、`ssh_manager` 全部由探测驱动；任何一项在另一平台上不可用时，理由必须区分
**这台机器上没装** 与 **这个平台还没有写入 Provider** 两种情况——代码里已经是两句不同的原文
（`internal/platform/platform_linux.go:690` 与 `internal/platform/platform_linux.go:692`，区分说明见 `internal/platform/platform_linux.go:686-688` 的注释），
Windows 侧对应 `"Windows 防火墙 Provider 在 M4 交付（当前版本只读展示）"`
（`internal/platform/platform_windows.go:82`）。

## M5 —— Windows 完整支持（把分布的能力收敛成受支持的 GA）

**这一节不引入新功能。** M5 的定位是项目一开始就敲定的那条："Linux 先行，抽象层从第一天就要能
为 Windows 服务"——抽象层确实是这么写的（下表），所以 M5 要交付的不是"再补一批 Windows 代码"，
而是**把散在 M0/M2/M4 里的 Windows 部分变成有安装/升级/回滚路径、有 CI、可以对外承诺的版本**。

### 5.2 M5 完成定义（必须逐条为真才算 GA）

| # | 验收项 | 判据 |
| --- | --- | --- |
| 1 | **安装 / 升级 / 回滚** | 存在受支持的 Windows 安装路径（服务注册走 `internal/platform/platform_windows.go:84` 的 `windows_scm`）；升级只换二进制，`panel.json`、`minipanel.db`（含会话、口令哈希、审计）与站点根目录保持不变；`store.go:74-75` 的"拒绝降级"在升级后仍然成立，因此回滚 = 回到**旧二进制 + 它写入时的 schema**，文档必须写清"回滚不需要改数据库，改了 schema 就不能回滚"这条后果；卸载后不留计划任务/服务/防火墙规则 |
| 2 | **全部 M2/M4 功能在 Windows CI 绿** | 站点创建与配置生成、php-cgi 池、预编译 DLL 扩展、WFP 规则写入与 `Snapshot()`/`Restore()`、SCM 服务启停、Web 终端、监控采集，在 Windows runner 上有**断言**而不是"能编过"；`make build-all` 的 4 OS × 2 arch 是前提而非结论（§6 矩阵） |
| 3 | **伪装与入口在 IIS-less 部署下可用** | 面板自己就是 web server，不挂 IIS/ARR/反向代理（`cmd/minipanel/main.go` 的包注释："There is no separate web server"），监听端口即面板端口；`unauth_status` 的中性 HTML 页与 444 断连、`mp_entrance` Cookie、TLS fail-closed 在 Windows 上与 Linux 行为一致，`TestEntranceGateDisguisesEverythingElse` 一类用例必须在 Windows runner 上跑绿 |
| 4 | **提权语义清楚** | 未提权时写操作报"这台机器不允许，因为进程令牌未提权"，而不是 500 或静默失败（`isElevated()` 在 `platform_windows.go:123-127`，判的是进程令牌）；`IsPrivileged=false` 不得被 UI 当作能力位 |
| 5 | **位图仍然诚实** | M5 之后 `internal/platform/capabilities_test.go:179` 的白名单里新增的每一项，都必须有对应的跨平台实现与 `Allow()` 调用；`SupportsSubSecondCron`（`capabilities.go:150`）仍只在面板内置调度器下为真，因为 `schtasks` 没有秒级 recurrence |

**不算 M5 的**：让 Windows 与 Linux 逐字节相同（POSIX 权限位就是没有）；把面板做成 IIS 站点或
Windows Service 之外的形态；在 Windows 上引入 cgo 或 MSVC 工具链——`CGO_ENABLED=0` 是硬要求（§6）。

## M6 —— 计划任务与备份

依据位图理由原文："计划任务调度器在 M6 交付"（`internal/platform/detect.go:59`）、
"备份任务与归档管理在 M6 交付"（`internal/platform/detect.go:58`）。

* 调度器：面板内置调度器（`capabilities.go:64` 的 `SchedPanel`，注释即 "always available"）与
  系统调度器（`crontab` / `taskschd`）两条路径都实现；`SupportsSubSecondCron` 只在面板内置
  调度器下为真，理由见 `platform_windows.go:91-93` 与 `capabilities.go:150` 的注释。
* 写系统 crontab 必须是"读-改-写 + 保留他人条目"，且写入前留备份，出问题可还原。
* 备份任务：归档产物落在 `BackupRoot()`（Linux `/www/backup`，Windows `C:\wwwbackup`，
  `platform_linux.go:60` / `platform_windows.go:31`），任务本身进审计；恢复路径要有明确确认。
* 与 M3 数据库备份、M2 站点备份共用同一套归档命名与保留策略。

**验收要点**：`cron`、`backup` 两个 feature 打开前，调度与备份的实际执行必须已在测试里被覆盖
（不允许"位图说会跑，代码里没人调用"）；任务失败要能被审计与日志同时看见。
